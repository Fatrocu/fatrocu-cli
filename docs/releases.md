# Signed release packaging

Updates use published stable GitHub Releases, never main. Candidate builds are not published or installed automatically. A release cannot be considered ready until normal tests and both private benchmark gates pass.

Artifact names are `fatrocu-cli-windows-x86_64.zip`, `fatrocu-cli-linux-x86_64.zip` and `fatrocu-desktop-windows-x86_64.zip` (replace architecture for another supported build). Archives contain flat files only. Windows CLI contains fatrocu-cli.exe and fatrocu-updater.exe. Desktop contains fatrocu.exe, fatrocu-updater.exe and fatrocu-server.exe. Keep application data and model files outside the installation and release archive. Poppler remains an explicit external dependency for PDF rendering.

Windows executable files and DLLs must be Authenticode-signed by the same confirmed publisher. Set FATROCU_TRUSTED_PUBLISHER_SHA256 to the SHA-256 fingerprint of that signing certificate, obtained independently from the publisher. This is a trust anchor, never a fingerprint taken from the candidate update itself. The updater checks Windows signature validity and exact certificate identity. The publisher identity has not yet been supplied for this project; signed installation validation remains pending. Do not invent a certificate identity or ship unsigned production updates.

Use scripts/package-windows.ps1 with a certificate already installed in the local certificate store to sign and package a CLI candidate. The script refuses to write an existing archive or use an invalid signature. Desktop packaging has the same requirements and also includes the server companion. Linux archives require a detached `<archive>.minisig` signed by the confirmed publisher; configure FATROCU_TRUSTED_MINISIGN_KEY independently. A checksum alone is insufficient.

After manual release publication, GitHub's asset metadata must expose `digest: sha256:<hex>`. Missing digests, wrong architecture, prereleases, drafts, absent helpers, wrong publisher, unsafe archive paths and failed checksums are rejected. Version checks use short timeouts, ETag caching and a six-hour startup cache; manual checks revalidate the cache. They send no document contents or telemetry.

Installation stages verified files away from the running application. The desktop closes only after its signed helper starts from a separate staging directory. The helper retries while the application exits, moves old files into a rollback directory, installs staged files and relaunches. Failed replacements restore previous files; rollback recovery files are preserved if restoring them fails. CLI Windows updates use the same bundled helper; Linux uses signed-archive verification and atomic replacement. Keep the installation writable by its owner; elevation and system-wide installers are not implemented.
